书影 Bookreel · 小说转视频 —— macOS 部署说明
（Apple Silicon，M3 Max 64GB 统一内存为基准）

Windows / RTX 4090 的那一套仍在 setup.bat 和 部署说明.txt 里，两边互不影响。
Mac 这边全部逻辑在 setup.command 一个文件里。

────────────────────────────────────────
为什么另起一个脚本
────────────────────────────────────────
不是换个后缀那么简单，四处是硬差异：

1. vLLM 和 CUDA 版 torch 在 Mac 上都不存在。llama.cpp 官方发布里有
   macos-arm64 的 Metal 预编译包，接口与 Windows 版完全一致，网页控制台
   不用改。
2. PyPI 上的 torch 在 macOS arm64 就是 Metal（MPS）版，不需要 get-torch
   那种“换源再验证”的绕法，直接 pip install torch 即可。
3. 显存不再是独立的一块。GPU 和 CPU 共用这 64GB，所以 nvidia-smi 那类体检
   没有对应物，脚本改看进程 RSS。
4. 视频那一档在 Mac 上没有本地实现（见下）。

────────────────────────────────────────
环境要求
────────────────────────────────────────
· Apple Silicon（M1 以上，本文按 M3 Max 64GB 调参），macOS 14 以上
· Xcode 命令行工具：xcode-select --install
· Python 3.11 或 3.12 最稳：brew install python@3.12
  3.13 / 3.14 下 ComfyUI 的部分依赖仍有轮子缺口
· ffmpeg（第 05 步合成用）：brew install ffmpeg
· 注意别在 Rosetta 下开终端。终端里 uname -m 必须是 arm64，
  出现 x86_64 的话 torch 会装成 CPU 版，Metal 全部失效。

────────────────────────────────────────
首次使用
────────────────────────────────────────
1. 终端里执行：chmod +x setup.command scripts/get-llama-mac.sh
   之后就可以在 Finder 里双击 setup.command
2. 选 1 安装环境（建 venv、拉 llama.cpp、克隆 ComfyUI）
3. 选 L 登录 Hugging Face
   在 https://huggingface.co/settings/tokens 建 READ token 粘进去
   再打开 https://huggingface.co/black-forest-labs/FLUX.2-dev 点 Accept
4. 选 2 下载权重
   把 models/flux2 里的权重放进 ComfyUI/models/ 对应目录：
     diffusion_models / text_encoders / vae
   ★ 与 4090 版相反：Mac 上优先用 bf16 版 unet，不要 fp8。
     MPS 没有 fp8 kernel，fp8 权重加载时会被升回 bf16，白下一遍。
5. 选 3 起常驻服务
6. 选 W 打开网页控制台
7. 想在本机出视频，再选 V 下 H3 权重（约 144GB），然后选 C 起档位 C

────────────────────────────────────────
与 4090 版的差异一览
────────────────────────────────────────
· 档位不再互斥
  24GB 显存装不下两个大模型，所以 Windows 版切档时会先 kill 上一档。
  这里 27B（约 17GB）＋ Flux.2（约 24GB）同时在内存里还有余量，
  默认不互斥。内存小的 Mac 把 setup.command 里的 EXCLUSIVE_SLOTS 改成 1
  就恢复旧行为。

· 小模型换到 :8001
  既然可以并存，Qwen3-8B 就不必和 27B 抢 :8000 了。:8001 正好是网页控制台
  “小模型”那一栏的默认值。

· 上下文从 16K 提到 32K
  KV cache 每 token 约 260KB，32K 大约吃 8GB，这里放得下。想要 64K 就把
  MAIN_CTX 改掉；再紧张可以加 KV_FLAGS="--cache-type-k q8_0 --cache-type-v q8_0"
  把 KV 砍一半。

· 权重可以不用压那么狠
  64GB 下 27B 的 Q5_K_M（19.8GB）甚至 Q6_K（23GB）都跑得动，
  改 setup.command 里的 F_MAIN_GGUF 即可。

· 常驻服务的设备
  检索向量走 mps，明显快；CosyVoice2 和 FunASR 留在 cpu ——
  它们会碰到 Metal 没有实现的算子，逐个回落到 CPU 反而比全程 CPU 更慢。
  三个服务现在都认 --device mps，想试就改 setup.command 顶部的
  EMBED_DEVICE / TTS_DEVICE / ASR_DEVICE。

· 后台运行 + 日志
  Windows 版每档开一个 cmd 窗口；这里统一用 nohup 丢后台，输出写到
  logs/<档位>.log，菜单里 T 可以直接 tail。菜单 F 只杀重档，
  常驻服务不动。

────────────────────────────────────────
视频那一档（档位 C）· MiniMax-H3 本地跑
────────────────────────────────────────
MiniMax 已经开源 H3 权重，antirez 又写了 h3.c —— Apple Silicon 上的原生
Metal 推理引擎（MIT）。所以档位 C 现在在 Mac 上能跑，只是慢。

怎么接进现有流水线
  services/h3_server.py 把 h3.c 包成一个 HTTP 服务，形状和 MiniMax 云端 API
  一样，网页控制台那边不用改任何东西：
    POST /v1/video/generations        提交，立刻返回 task_id
    GET  /v1/query/video_generation   轮询状态
    GET  /v1/files/<file_id>          取 mp4
  菜单选 C 就是起这个服务（端口 9000）。想用云端就把控制台里视频端点换成
  MiniMax 的地址，其余流程完全一致。

它替你兜住的两件事
  1. 分辨率。控制台按云端习惯请求 1080x1920，h3.c 的画布上限是
     768*1344 个像素、边长必须是 32 的倍数。服务端会自动换算成同比例下
     最大的合法画布（1080x1920 -> 736x1312），反正成片前还要超分。
     注意 720 不是 32 的倍数，所以 VIDEO_RES 从 720x1280 改成了 704x1280。
  2. 时长。H3 是 24fps，帧数只能是 5+17n，所以“10 秒”实际出 243 帧
     （10.125 秒）。

排队策略
  一次只跑一段。单段就要吃掉约 36GB 峰值内存并占满 GPU，并行只会一起变慢
  甚至换页。多提交的任务排队，控制台轮询等着就行。
  菜单 C 会先 kill 掉档位 A/B —— 这一档不参与"可以并存"那条规则。

有多慢
  h3.c 自己给的基准是 M5 Max、512x512、22 帧、20 步：约 12-17 秒。
  我们要的是 736x1312、243 帧，像素×帧数是它的四十倍上下，注意力还是超线性，
  而且 M3 没有 M5 的 int8 TensorOps，只能走 BF16。
  按这个推算，一段 10 秒大约要几十分钟；一章 42 段是按天算的。
  所以本地这条路适合试镜头、看构图，整章还是走云端或者留给 4090。

先跑通再说
  想快速验证装好了没有，先出一段小的：
    cd third_party/h3.c
    ./h3 -d ../../models/minimax-h3 -p "雪地上的红狐" \
         --width 512 --height 512 --frames 22 --steps 4 -o outputs/t.mp4
  几秒到几十秒就该出片。控制台那边的超时已经从 12 分钟放宽到 6 小时，
  轮询也从 3 秒放慢到 15 秒一次。

调质量/速度
  setup.command 顶部：H3_STEPS（默认 20，4 是预览档，50 是参考质量）、
  H3_LAYERS（40-50）、H3_REUSE（1 最好，2 是默认）、
  H3_EXTRA 可以加 --token-reduction（更快，构图可能变）。

许可证
  引擎 h3.c 是 MIT；权重走 MiniMax 社区许可（按营收设上限、部分国家排除），
  成片要商用之前自己读一遍。

自己部署的视频服务
  hailuo/server.py 存在的话，菜单 C 仍然优先起它，行为和 Windows 版一致。

────────────────────────────────────────
64GB 统一内存上的几条注意
────────────────────────────────────────
· macOS 默认只让 GPU 锁住约 3/4 的内存（64GB 上约 48GB）。Flux.2 出
  1080x1920 时可能顶到这个上限，菜单 M 会执行
    sudo sysctl -w iogpu.wired_limit_mb=57344
  要 sudo，重启后失效，不用时不占任何东西。
· 速度和显存是两回事。M3 Max 出图大约是 4090 的 1/3 到 1/5 快，
  但不会 OOM，也不用为了塞进 24GB 而降规格。文本推理的差距小得多。
· 出片仍建议 720x1280，成片前用 Real-ESRGAN 统一超分到 1080x1920。
· reasoning_effort 照旧：改写剧本给 xhigh，批量切片和写 prompt 用 low。
· 跨域：llama.cpp 默认允许；ComfyUI 由脚本带 --enable-cors-header "*"。

────────────────────────────────────────
排错
────────────────────────────────────────
· “llama-server 已损坏 / 无法验证开发者”
  下载来的二进制带 com.apple.quarantine。get-llama-mac.sh 已经会执行
  xattr -dr com.apple.quarantine llama/，手动补一次也行。

· torch.backends.mps.is_available() 是 False
  九成是终端在 Rosetta 下。检查：
    python3 -c "import platform;print(platform.machine())"   # 要 arm64
  另一成是 venv 建在 x86 的 python 上，删掉 venvs/ 重跑菜单 1。

· ComfyUI 报 “not implemented for MPS”
  脚本已经导出 PYTORCH_ENABLE_MPS_FALLBACK=1，这类算子会回落到 CPU；
  如果仍然直接抛错，说明那一步在自定义节点里，升级该节点或换个采样器。

· 出图到一半被系统杀掉
  先执行菜单 M 抬高 wired limit；仍不行就给 COMFY_EXTRA 加 --lowvram。

· 端口被占
  菜单 3 会跳过已经在监听的服务。要重启某个服务，先菜单 F 或
  kill 掉 logs/<名字>.pid 里的进程。

· 双击 Pipeline Runner.dc.html 打开是一片空白
  它不能当本地文件打开。support.js 里的 dc runtime 启动时要
  fetch(location.href) 把自己再读一遍，file:// 下浏览器不允许，页面就停在
  空白。走菜单 W —— 它会先起 services/web_server.py，再打开
  http://127.0.0.1:8080/Pipeline%20Runner.dc.html

· 想在手机或另一台机器上用
  1) 把 setup.command 顶部的 BIND_LAN 改成 1
  2) 菜单 F 停掉正在跑的档位，菜单 3 重起常驻服务（要重起才会换绑定地址）
  3) 菜单 W，终端会打印形如 http://192.168.x.x:8080/... 的地址
  4) 手机连同一个 Wi-Fi，浏览器打开那个地址
  控制台里的端点默认跟着页面地址走，会自动指向这台 Mac，不用手改。
  BIND_LAN=1 等于把大模型、出图、出片服务一起摆到局域网上，它们都没有口令，
  只在信得过的网络里这么做。用完把 BIND_LAN 改回 0 再重起服务。
